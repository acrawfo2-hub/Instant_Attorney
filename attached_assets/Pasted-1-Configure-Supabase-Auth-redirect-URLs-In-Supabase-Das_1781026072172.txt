2) Confirm your /api/auth/callback handler matches the expected flow
Your route needs to exchange the confirmation token into a session (using verifyOtp / exchangeCodeForSession depending on the flow Supabase uses for confirmation links).

For typical email confirmation links, you’ll receive query params like token_hash and type=email.

So inside app/api/auth/callback/route.ts you should:

read token_hash and type from request.url
create a server Supabase client (cookie-enabled)
call supabase.auth.verifyOtp({ token_hash, type })
redirect the user to an appropriate page (often / or /account)

3) Ensure your server API route uses the cookie-based SSR client
In App Router API routes, you typically need createServerClient from @supabase/ssr so Supabase can set auth cookies in the response.

If you’re currently using a plain createClient (from @supabase/supabase-js) in the server route, it often causes “confirmation succeeded but user is not logged in” issues.

4) Common failure causes (given your setup)
Redirect URL mismatch
Your email link sends the browser to /api/auth/callback, but the Supabase redirect allow list doesn’t include that exact URL(s).
Callback route doesn’t actually verify the OTP

Callback route uses wrong Supabase client / no cookies
Cookies aren’t being set, so the session is missing after redirect.
